# CLAUDE.md — Waves Customer Portal

Context for Claude Code sessions working on the waves-customer-portal monorepo.

## Dev Workflow

- Subagents that only search, read logs, or run tests pass `model: sonnet`
  (or `haiku`) — a search agent inherits the main model otherwise.
- Start the app only when the authorized task needs runtime verification.
  Read-only audits and explanations do not require startup.
- Before startup, verify the selected checkout, command hooks, database
  environment, and integration side effects without printing credentials.
  Follow `docs/development.md`: run `worktree:setup` and the relevant
  `dev:doctor` preflight before managed startup. Frontend-only verification
  uses `dev:managed-client` (or standalone `dev:client`). Full startup
  requires a verified dedicated dev/preview database and isolated integrations.
  Managed `dev` checks readiness without migrating; `dev:migrate` is explicit.
- Diagnose task-relevant startup failures. Report unrelated failures and
  continue independent authorized work; do not expand the task to fix them.

## Rules

1. **Only touch what you're asked to touch.** If the task is "add a tool to the Intelligence Bar," don't refactor the route file, don't update the UI theme, don't reorganize imports in unrelated files.
2. **Don't add features that weren't requested.** No "while I'm here, I also improved..."
3. **Don't guess at business logic.** Retrieve applicable owner-approved decisions and authoritative contracts first, preserving their scope. Ask when the decision is missing, conflicting, or would change; do not ask the owner to repeat an applicable decision.
4. **Match the file's existing style.** Don't mix `D` palette with `components/ui` primitives in the same component.
5. **Don't delete or rename existing files** without explicit instruction. Don't move files between directories.
6. **Test your SQL.** Every Intelligence Bar tool runs Knex queries against PostgreSQL. Wrap uncertain tables/columns in try/catch — don't crash a tool module on one bad query.
7. **Keep the Intelligence Bar pattern.** Tool modules export `TOOLS` + `executeTool`; wire 6 lines into the route file. Don't invent a new architecture. See `server/services/intelligence-bar/README.md` for the template.
8. **Stripe is the payment processor. Square is fully phased out.** Do not reference Square in new code.
9. **All automation and site infra is native.** Do not reference Zapier, Make, Elementor, NitroPack, RankMath, or any external automation/CMS tool in new code.
10. **Plan first for non-trivial work.** For anything beyond a small, well-specified change, present a plan and get sign-off before writing code. An already-approved plan does not need another sign-off for unchanged implementation steps. Reconfirm a material change in effect, environment, scope, or risk. Investigation and proposal-only work may proceed within their authorized scope. Bring unresolved design, functionality, and intended-behavior decisions to the owner; make routine technical execution decisions within the approved scope autonomously, including review fixes, PR splits, and re-tagging Codex. For authorized shipping tasks, own review follow-through, merge clean non-blast-radius PRs, and continue already-authorized work in the same lane under `waves-ship` §§4–5; preserve its explicit stop conditions and narrower user instructions.
11. **When a mistake is caught, diagnose the cause.** Follow `/lesson` or `.claude/commands/lesson.md` to strengthen the existing rule, skill, regression check, or environment fix. Preserve task scope: proposal-only work returns proposed edits; authorized fixes include any necessary correction in the same change. Do not add permanent prose for temporary status or an already-clear rule.
12. **Never send or trigger customer-facing communications** (SMS, email, calls) — the owner sends all. Before any prod action, check for comm side effects (editing/completing/rescheduling `scheduled_services` rows can fire confirmation/reminder SMS) and route around them.
13. **Never test on real customers' live records.** "No durable writes" is not the safety bar (e.g. slot holds block real bookings). Use the staff draft-preview paths or owner-created test records; read-only DB inspection is fine.
14. **Hands-off + exception-based by default.** Deterministic green checks auto-apply with an audit trail and no bell; only exceptions park and surface; every lane keeps an env kill switch + one-click revoke. Where a human decision is genuinely required, use the email-reply approval pattern — a tokenized email to contact@ answered by replying "approved"/"not approved", fail-closed, at-most-once (current in-repo exemplars: the newsletter proof flow in `server/services/newsletter-proof.js`, and the content-lane approvals in `server/services/content/email-approvals.js` from PR #3024, which handle only autonomous-content review kinds) — never a park-on-portal-visit queue. Never extend email-approval to customer comms, money movement, or gate flips.
15. **Find the existing mechanism before building one.** Before adding a new page, tab, AI assistant, queue, or action system, check whether the capability belongs in an existing canonical workflow (see `docs/audits/admin-simplification/capabilities.md`). Search for the nearest existing implementation first. Canonical paths that must not grow siblings: surcharge math = `computeChargeAmount` (`server/services/stripe-pricing.js`), tracker state = `server/services/track-transitions.js`, ET wall-clock = `server/utils/datetime-et.js` on the server and `client/src/lib/timezone.js` in React (the client companion — never import the server module into the Vite bundle), admin auth = `adminAuthenticate` + role check from `server/middleware/admin-auth.js` (router-level `router.use(…)` in `admin-*.js` files; per-handler on mixed public/staff routers like `badges.js`), per-user feature flags = the `user_feature_flags` DB read via `useFeatureFlag` on the client and `isUserFeatureEnabled` (`server/services/feature-flags.js`) for authoritative server-side checks, release/dark-ship gates = `GATE_*` env flags via `server/config/feature-gates.js` (distinct mechanisms — per-user capability vs deploy-wide rollout), Intelligence Bar tools = `TOOLS` + `executeTool`. Extending the canonical path beats a working local duplicate.
16. **Make the smallest coherent change.** Prefer the shared mechanism over a local workaround, but don't generalize past the demonstrated requirement: no single-use wrappers, factories, or config, and no release machinery (compat layers, dual-writes, fallback paths) beyond the standard `GATE_*` dark-ship pattern unless a specific deployment risk is named.
17. **Trace the change end-to-end before claiming done.** UI → route → service → DB → response → UI state, plus side effects (webhooks, crons, SMS, cache, analytics). Verify column names, APIs, and env vars against the code — never invent them.
18. **Contracts get deliberate treatment; internals don't.** Identify consumers before touching a boundary: DB schema and CHECK-constrained values, public `/:token` routes (contracts in `docs/public-route-contracts.md`), every inbound webhook payload shape — the provider owns the contract, so this covers any webhook route mounted in `server/index.js` (today: Stripe, Twilio, SendGrid, Resend, Bouncie, the ElevenLabs voice-agent), including ones added after this list, endpoints consumed by the iOS and Android apps (push/app-link payloads included), Astro spoke-fleet form posts and feeds, the retained V1 named exports, persisted identifiers. Internal shapes (a handler's private helpers, local state, query structure) may change without ceremony once their consumers are migrated — but every repository-wide correctness and security rule (AGENTS.md P0/P1: auth, parameterized SQL, surcharge math, ET handling, status constraints) still applies inside handlers.
19. **Remove the code you supersede.** When replacing behavior, delete the obsolete helper, flag read, export, or branch in the same PR unless compatibility requires keeping it. Whole-file deletions still require explicit instruction per rule 5 — propose the deletion in the PR body and leave the file until authorized. State in the PR what became obsolete.
20. **Judge complexity qualitatively, not numerically.** A simplification must remove decisions (dedupe checks, delete dead branches, table-drive repeated conditionals), not relocate them into one-use helpers to lower a metric. New tests name the observable behavior, credible regression, and gap in existing proof; extend an existing case when possible. Preserve independent contracts, including static guards. Use the `waves-test-audit` skill for test-value audits or consolidation; ordinary changes need no sweep.

Commercial suite sizing (`server/services/commercial-suite-size/`): `GATE_COMMERCIAL_SUITE_SIZING` — **ships DARK: off unless exactly `true`**, read at call time via `commercialSuiteSizingLive()` (`server/config/feature-gates.js`); off = byte-identical to before. When on, an estimator-engine call draft for a commercial tenant in a multi-tenant building (unit scope `commercial_suite`, e.g. a restaurant in unit 102 of a plaza) is priced off the SUITE's own square footage, never the whole building and never a $0 manual quote: caller/tech-stated size (source-arbitration.js, unchanged) → an active FL DBPR permanent food-service license naming that suite (`dbpr-food-license.js`: public CSV extract, 24h in-process cache, bounded fetch + 10-minute failure backoff; seats → sq ft) → a type default keyed off `commercialRiskType`/`commercialSubtype` only (`type-defaults.js`). A license size parks the draft yellow ("confirm on site"); a type default also prices LOW confidence (`footprintSizeEstimated`, applied once in `generateEstimate` to every commercial line), so the low-confidence delivery gates apply. Requires `GATE_UNIT_SCOPE_GUARDRAILS` (on in prod) — that apply is what clears the building size a suite is sized in place of; with guardrails off the engine skips suite sizing and logs a warning. `COMMERCIAL_SUITE_WEB_SEARCH` — default ON, read at call time; `0`/`false`/`off` disables the business-name web-search leg (`web-search-leg.js`, via `services/llm/call.js` `callAnthropic`), which is NEVER a size source (AGENTS.md: an LLM proposes intent, it never reaches a price/size field) — it only names the business in the draft notes when the license has nothing.
