# WavesPay — the Waves Admin iPhone app

Native iOS app, shown on the home screen as **Waves Admin**. It opens the staff
portal (`/admin`, which lands technicians on Field Tools) in a web view and
takes card payments itself with Stripe Terminal's **Tap to Pay on iPhone** (no
separate reader hardware — the iPhone's NFC chip is the reader). A Tap to Pay
button on a staff page opens Apple's tap sheet over that page, and the page
learns the result, so a payment never leaves the app.

The folder, Xcode target and bundle id keep the WavesPay name
(`com.wavespestcontrol.wavespay`): the Tap to Pay approval belongs to that
App ID. A `wavespay://collect?t=<jwt>` link from Safari still opens the app and
takes the payment, as before.

3. Xcode → **Product → Destination** → choose your device.

1. In Waves Admin, open a visit's checkout (or an unpaid invoice) and tap

2. The page calls `/handoff` and hands the returned

4. Tap **Tap to Collect** — Apple's Tap to Pay sheet appears.
5. Tap a test card (Stripe's test cards work in TEST mode; real cards

6. The page under the sheet already moved on: checkout continues the way
   it does after any card payment. The invoice flips to paid via the usual
   Stripe webhook.

## Architecture in one paragraph

The portal's PWA never hand-rolls a `wavespay://` URL; it always calls
`/api/stripe/terminal/handoff` first, which mints a 60-second HMAC-signed
JWT with an embedded `jti`, `invoice_id`, and `amount_cents`, and returns
the deep link. iOS parses the `t` parameter, decodes the JWT's `jti` claim
locally (the server verified the signature), and hits `/validate-handoff`
to atomically burn the `jti` and fetch the authoritative invoice state,
including the invoice number and what the customer pays for: its service
lines and the totals rows the invoice PDF prints, down to the amount due
(prices are left off when those rows do not add up to the charge).
The tech then taps **Tap to Pay on iPhone**; iOS hits `/payment-intent` with the `jti`
to create a `card_present` PaymentIntent scoped to that handoff row.
Stripe Terminal's on-device flow takes over: discover the synthetic
Tap-to-Pay reader, connect, collect payment method (NFC sheet appears),
confirm. Success goes back to the portal via the existing Stripe webhook.

Inside the app, the page and the app talk over one bridge
(`Sources/PortalView.swift`; page side `client/src/lib/tapToPay.js`). The
page posts `{ type: 'tapToPay', requestId, deepLink }` to
`window.webkit.messageHandlers.wavesAdmin`; the app accepts it only from the
portal's own top page and answers that request exactly once with a
`wavesadmin:taptopay` window event, `detail = { requestId, status:
'succeeded' | 'failed' | 'canceled', invoiceId?, paymentIntentId?, message? }`.
The answer only tells the page to move on; the webhook still marks the
invoice paid.

Connecting the phone's tap reader is the slow step (seconds), so the app
connects it before the first tap: when a signed-in staff page loads, when
the app comes back to the front, and when a payment link checks out. A
signed-in staff page posts `{ type: 'prepareReader' }` and defines
`window.wavesAdminConnectionToken()`, which fetches a Stripe connection
token from `/connection-token` under the page's own sign-in. The app asks
the page for each token and falls back to the payment's terminal token.

## Staff alerts

Web push cannot run in the app's web view, so staff alerts arrive as iPhone
notifications (APNs). After sign-in the staff page posts
`{ type: 'registerPush' }`; the app asks for notification permission once and
answers with a `wavesadmin:pushtoken` window event (`{ token, environment }`).
The token is registered even when permission is denied: iOS only hides the
alerts, so allowing them later in iPhone Settings needs no new sign-up.
The page registers the token under its own sign-in at
`POST /api/admin/push/native-subscribe` (`client/src/native/wavesAdminPush.js`);
the row names this app's bundle and APNs environment (Xcode installs use the
sandbox), and `server/services/apns.js` sends to the matching topic and host.
The page sets the icon badge with `{ type: 'badge', count }`. A tap on an
alert opens its portal page: the app sends a cancelable `wavesadmin:openlink`
event (`{ url }`) to the main view, and a signed-in staff page takes it and
navigates itself, so its unsaved-changes prompt and the field visit lock still
apply. With no such page (a cold start, the sign-in page) the app loads the
link directly. Only the main view registers; a portal popup shares its sign-in.

## Security notes

- The JWT's signature is verified server-side on `/validate-handoff`. The
  client only reads claims; never trust `jti`, `amount_cents`, or
  `invoice_id` from a decoded-but-unverified token for anything that
  matters.
- The app has no sign-in of its own. Staff sign in on the portal page
  (its token stays in the web view's storage, as in Safari).
  `/validate-handoff` returns a 15-minute terminal-scoped token for the
  payment's `/connection-token`, `/payment-intent` and `/apply-surcharge`
  calls; it lives in Keychain (`kSecAttrAccessibleAfterFirstUnlock`), and
  launch deletes any token an older WavesPay build saved.
- The reader warm-up keeps the staff sign-in in the web view too: the page
  hands the app only the Stripe connection token, never the staff token.
- No Face ID lock yet. The app holds a full staff session, the same as the
  home-screen web app. The charge authorization lives in the handoff token
  (60-second TTL, one-time use).
- Links to other sites, phone numbers and maps open outside the app;
  `window.open` pages from the portal open in an in-app sheet that shares
  the sign-in.

## Troubleshooting

- **`./bootstrap.sh` fails with "xcodegen: command not found"** — Homebrew
  install silently failed. Run `brew install xcodegen` manually and
  re-run the script.
- **"No tap-to-pay reader found"** during discovery — most likely cause:
  the entitlement isn't applied to this build, or the app is running in
  the simulator. Confirm on a real device; in Signing & Capabilities
  verify the proximity-reader entitlement is listed.
- **"This payment timed out"** — the 15-minute terminal token expired
  (the amount screen sat open). Close it and tap Tap to Pay again.
- **410 `replay` on `/validate-handoff`** — the token was already used.
  The portal's Charge now button needs to mint a fresh handoff.
- **409 `invoice_amount_changed`** — admin edited the invoice total
  between mint and validate. Close the flow and re-tap Charge now.

## What's intentionally NOT here (future work)

- A full receipt inside the app. The success screen shows the amount
  charged and the card; the portal's own receipt email and SMS do the rest.
- Manual PaymentIntent retrieval / retry UI. If the NFC flow errors out,
  the tech re-handoffs — simpler than maintaining an iOS-side retry
  state machine.
- Background reader keep-alive. The SDK disconnects when the app is
  backgrounded and reconnects by itself when it comes back; the app
  connects again if that fails.
- A custom launch screen.
