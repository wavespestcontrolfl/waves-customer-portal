# WavesPay — the Waves Admin iPhone app

Native iOS app, shown on the home screen as **Waves Admin**. It opens the staff
portal (`/admin`, which lands technicians on Field Tools) in a web view and
takes card payments itself with Stripe Terminal's **Tap to Pay on iPhone** (no
separate reader hardware — the iPhone's NFC chip is the reader). A Tap to Pay
button on a staff page opens Apple's tap sheet over that page, and the page
learns the result, so a payment never leaves the app.

The folder, Xcode target and bundle id keep the WavesPay name
(`com.wavespestcontrol.wavespay`): the Tap to Pay approval belongs to that
App ID. A `wavespay://collect?t=<jwt>` link from Safari still opens the app and
takes the payment, as before.

### 3. Generate the Xcode project

```bash
./bootstrap.sh
```

This installs XcodeGen via Homebrew if missing, runs `xcodegen generate`

Re-run whenever project.yml changes.

1. `open WavesPay.xcodeproj`
2. Select the `WavesPay` target → **Signing & Capabilities**.
3. Confirm **Team** shows "Waves Pest Control LLC" (the `BMNXJ4Q89M`

5. Set `STRIPE_TERMINAL_LOCATION_ID` in `project.yml`, then run the repository's

### 5. Install on a real iPhone

1. Register the device UDID at
   https://developer.apple.com/account/resources/devices/list if it's
   not already there (Adam's, Jose's, Jacob's).
2. Plug the iPhone into your Mac.
3. Xcode → **Product → Destination** → choose your device.
4. Run (⌘R). First launch prompts for location permission — allow.
5. The staff portal opens. Sign in there, with the two-step code.

### 6. Test the flow end-to-end

1. In Waves Admin, open a visit's checkout (or an unpaid invoice) and tap
   **Tap to Pay on iPhone** (**Charge in person** on the invoices page).
2. The page calls `/handoff` and hands the returned
   `wavespay://collect?t=<jwt>` link to the app — no app switch.
3. The app validates the token and slides up the amount + customer name.
   The first time, Apple's "How to Tap" lesson shows (iOS 18+).
4. Tap **Tap to Collect** — Apple's Tap to Pay sheet appears.
5. Tap a test card (Stripe's test cards work in TEST mode; real cards
   work in LIVE). You see the success screen; tap **Done**.
6. The page under the sheet already moved on: checkout continues the way
   it does after any card payment. The invoice flips to paid via the usual
   Stripe webhook.

The old path still works: Safari's Tap to Pay button opens the app with the
same link, and the app takes the payment over the portal page.

## Architecture in one paragraph

The portal's PWA never hand-rolls a `wavespay://` URL; it always calls
`/api/stripe/terminal/handoff` first, which mints a 60-second HMAC-signed
JWT with an embedded `jti`, `invoice_id`, and `amount_cents`, and returns
the deep link. iOS parses the `t` parameter, decodes the JWT's `jti` claim
locally (the server verified the signature), and hits `/validate-handoff`
to atomically burn the `jti` and fetch the authoritative invoice state,
including the invoice number and what the customer pays for: its service
lines and the totals rows the invoice PDF prints, down to the amount due
(prices are left off when those rows do not add up to the charge).
The tech then taps **Tap to Pay on iPhone**; iOS hits `/payment-intent` with the `jti`
to create a `card_present` PaymentIntent scoped to that handoff row.
Stripe Terminal's on-device flow takes over: discover the synthetic
Tap-to-Pay reader, connect, collect payment method (NFC sheet appears),
confirm. Success goes back to the portal via the existing Stripe webhook.

Inside the app, the page and the app talk over one bridge
(`Sources/PortalView.swift`; page side `client/src/lib/tapToPay.js`). The
page posts `{ type: 'tapToPay', requestId, deepLink }` to
`window.webkit.messageHandlers.wavesAdmin`; the app accepts it only from the
portal's own top page and answers that request exactly once with a
`wavesadmin:taptopay` window event, `detail = { requestId, status:
'succeeded' | 'failed' | 'canceled', invoiceId?, paymentIntentId?, message? }`.
The answer only tells the page to move on; the webhook still marks the
invoice paid.

Connecting the phone's tap reader is the slow step (seconds), so the app
connects it before the first tap: when a signed-in staff page loads, when
the app comes back to the front, and when a payment link checks out. A
signed-in staff page posts `{ type: 'prepareReader' }` and defines
`window.wavesAdminConnectionToken()`, which fetches a Stripe connection
token from `/connection-token` under the page's own sign-in. The app asks
the page for each token and falls back to the payment's terminal token.

## Staff alerts

Web push cannot run in the app's web view, so staff alerts arrive as iPhone
notifications (APNs). After sign-in the staff page posts
`{ type: 'registerPush' }`; the app asks for notification permission once and
answers with a `wavesadmin:pushtoken` window event (`{ token, environment }`).
The token is registered even when permission is denied: iOS only hides the
alerts, so allowing them later in iPhone Settings needs no new sign-up.
The page registers the token under its own sign-in at
`POST /api/admin/push/native-subscribe` (`client/src/native/wavesAdminPush.js`);
the row names this app's bundle and APNs environment (the signing profile's
`aps-environment`: development-signed installs, Debug or Release, use the
sandbox), and `server/services/apns.js` sends to the matching topic and host.
The page sets the icon badge with `{ type: 'badge', count }`. A tap on an
alert opens its portal page: the app sends a cancelable `wavesadmin:openlink`
event (`{ url }`) to the main view, and a signed-in staff page takes it and
navigates itself, so its unsaved-changes prompt and the field visit lock still
apply. With no such page (a cold start, the sign-in page) the app loads the
link directly. Only the main view registers; a portal popup shares its sign-in.

## Sign in with Google

Google refuses OAuth inside a web view (403 `disallowed_useragent`), so the
sign-in page asks the app to run it. The page posts
`{ type: 'googleSignIn', challenge }` (`challenge` = 43 base64url characters);
the app accepts it only from the main view and opens Apple's sign-in sheet
(`ASWebAuthenticationSession`, shared Safari cookies) at
`/api/admin/auth/google/start?client=ios&challenge=<challenge>`. The server
ends the flow at `wavespay://google-signin?result=<43 base64url chars>` or
`?error=<reason>`. The app answers the page with a `wavesadmin:googlesignin`
window event, `detail = { result }` or `{ error }` (`canceled`, `busy`,
`failed`, or the server's reason). A bad challenge answers `failed`; a second
request while a sheet is open answers `busy`. The page side is
`client/src/native/wavesAdminGoogleSignIn.js`; it detects support by the
`WavesAdmin/1.7` user agent. A `wavespay://google-signin` link that reaches
`handleIncomingURL` is ignored and never starts a payment.

## Bridge messages: customer hand-off and save card (1.9)

Book at the Table: the owner hands his admin phone to a customer to save a
card. The customer never sees the signed-in admin web view. The admin page asks
the app to open the secure card page in a separate screen (`NativeBridge.swift`,
`CustomerHandoff.swift`).

**Admin page** (handler `wavesAdmin`; the app answers once with a window event
on the web view that asked; `requestId` comes back unchanged):

| Page posts | App answers (event: `detail`) |
| --- | --- |
| `{ type: 'capabilities', requestId }` | `wavesadmin:capabilities`: `{ requestId, capabilities: ['handoffOpen'] }`, or `capabilities: []` on an iPhone that cannot ask for Face ID, Touch ID or the passcode (no passcode set) |
| `{ type: 'handoffOpen', requestId, url, firstName }` | `wavesadmin:handoff`, once, when the hand-off ends: `{ requestId, status: 'ended' }`, or `{ requestId, status: 'failed', message }` (also on an iPhone with no passcode) |

`url` must be the portal's own origin, a path starting `/secure/<token>` and
`handoff=1`; anything else answers `failed`.

**Customer view.** A full-screen screen that cannot be swiped away:
- A new web view with a non-persistent data store (no admin cookies,
  localStorage or IndexedDB), and one bridge handler, `wavesCustomer`. It has
  no `wavesAdmin` handler, no connection-token, push or badge paths.
- Main-frame loads stay on the portal's `/secure/` pages (and `about:blank`).
  Frames inside the page (Stripe card fields) load. Everything else, including
  tel:, sms:, mailto:, other sites, downloads and new windows, is blocked
  silently; nothing opens outside the app.
- A top bar "Handed to {firstName}" with **Hand back**: Face ID / Touch ID with
  the passcode as fallback (`.deviceOwnerAuthentication`, reason "Take the
  phone back"). Success closes the screen and answers the admin page `ended`.
  Cancel or failure stays on the customer view. Only a passed check ends it:
  the app never starts a hand-off on an iPhone with no passcode, and if the
  passcode is turned off during one, the lock stays until a passcode is set
  again. Hand back is ignored (the bar says "Finishing the card save…") while a terms or save request is pending or the card-save screen is open; a request that finishes after the hand-off ends opens nothing.
- Opening it pauses the staff alerts (`StaffAlerts.pauseForHandoff`): the
  alerts already in Notification Center are cleared and the install
  unregisters from APNs, so none shows in the list, on the lock screen or with
  the app in the background (a push sent meanwhile gets Unregistered and the
  server deactivates the row). One that still arrives with the app open shows
  only the badge. While the flag is on, `register()` (a `registerPush` from
  the covered admin page, or a task still waiting) does not register, and a
  token that arrives late unregisters again and is not sent to the page. A
  successful Hand back registers again
  (`resumeAfterHandoff`); the token event re-sends `native-subscribe`, which
  turns the row active again. The flag is `handoffLockActive` in UserDefaults;
  sign-out clears it without turning the alerts back on.
- If the app restarts with the flag still on (it was closed during a hand-off),
  the customer view is gone. `RootView` shows a "Waves Admin is locked" screen
  INSTEAD of the portal: the portal web view is not created, so it shows
  nothing and takes no input, until the same device check passes (nothing
  else unlocks it). Wavespay payment links are ignored meanwhile.
  Logic check for the flag:
  `swiftc -o /tmp/handoff-check Sources/HandoffLock.swift Tests/main.swift &&
  /tmp/handoff-check`.

**Customer page** (handler `wavesCustomer`; answers are window events on the
customer web view; accepted only from its top frame on a `/secure/` page):

| Page posts | App answers (event: `detail`) |
| --- | --- |
| `{ type: 'capabilities', requestId }` | `waveshandoff:capabilities`: `{ requestId, capabilities: ['saveCard'] }` |
| `{ type: 'saveCard', requestId, consentTextVersion, agreed, feeDisclosedAmount, disclosureVersion }` | `waveshandoff:savecard`: `{ requestId, status: 'succeeded', card: { brand, last4, funding } }`, `{ status: 'failed', message }`, or `{ status: 'canceled' }` |

The customer page holds no staff credential (it accepts the estimate terms
through its own secure link, with no app relay). For `saveCard` the app calls
`window.wavesAdminSaveCardHandoff({ secureToken, consentTextVersion, agreed,
feeDisclosedAmount, disclosureVersion })`, which resolves `{ deep_link }`
(`wavespay://save-card?t=<jwt>`). `secureToken` is the token in the opened URL
path, never read from the customer page. A missing or throwing admin function
answers `failed` with a plain message.

**Save card.** From the deep link the app posts the token to
`/stripe/terminal/validate-save-card-handoff`, connects the reader (the
returned `auth_token` fetches the connection token when no signed-in page
did), then `retrieveSetupIntent`, `collectSetupIntentPaymentMethod(_:allowRedisplay: .limited)`
and `confirmSetupIntent` (Apple's tap sheet), and last posts
`/stripe/terminal/complete-setup { setup_intent_id }`. It never shows an
amount or a surcharge and never calls `/payment-intent` or `/apply-surcharge`.
`failed.message` is the server's `error` text when it sent one. One card save
or payment at a time (`AppState.cardSaveOpen`). A `wavespay://save-card` link
opened from Safari starts nothing: the app shows "Open this from Waves Admin."

### Manual test checklist (real iPhone, TestFlight or Xcode build)

1. Admin page posts `capabilities`: answer is `['handoffOpen']`.
2. `handoffOpen` with a bad url (other host, `/admin/...`, no `handoff=1`):
   answer `failed`; no screen opens.
3. `handoffOpen` with a good url: the customer view opens full screen with
   "Handed to {name}". Swiping down does nothing.
4. In the customer view, open Safari's Web Inspector (Debug build): no admin
   cookies or localStorage; `window.webkit.messageHandlers.wavesAdmin` is
   undefined; `wavesCustomer` is defined.
5. Tap a tel:, sms:, mailto: or outside link on the page: nothing happens.
6. Start a hand-off with staff alerts in Notification Center: they are gone.
   Send a staff alert, app open and then in the background: nothing shows
   (no banner, no sound, no list entry, nothing on the lock screen).
7. Customer page `capabilities`, `saveCard`: answers as above.
   Run a full card save: "Getting the card reader ready…", Apple's sheet,
   "Saving the card…", "Card saved", then `succeeded` in the customer view.
8. `saveCard` when the admin function is missing (older admin page): `failed`.
9. Customer closes Apple's sheet: `canceled`.
10. **Hand back**, cancel Face ID: stays on the customer view. Pass Face ID:
    the admin page gets `ended`; the next alert shows a banner.
11. Phone with no passcode: `capabilities` answers `[]` (no hand button) and
    `handoffOpen` answers `failed` ("Set a passcode on this iPhone first…").
12. Force-quit during a hand-off, relaunch: "Waves Admin is locked" replaces the
    portal (not loaded) until Face ID passes; alerts stay silent until then.
13. Open `wavespay://save-card?t=x` from Safari: "Open this from Waves Admin."
14. Existing `tapToPay`, `prepareReader`, `registerPush` still work, and
    `tapToPay` during a card save answers `failed`.

## Security notes

- The JWT's signature is verified server-side on `/validate-handoff`. The
  client only reads claims; never trust `jti`, `amount_cents`, or
  `invoice_id` from a decoded-but-unverified token for anything that
  matters.
- The app has no sign-in of its own. Staff sign in on the portal page
  (its token stays in the web view's storage, as in Safari).
  `/validate-handoff` returns a 15-minute terminal-scoped token for the
  payment's `/connection-token`, `/payment-intent` and `/apply-surcharge`
  calls; it lives in Keychain (`kSecAttrAccessibleAfterFirstUnlock`), and
  launch deletes any token an older WavesPay build saved.
- The reader warm-up keeps the staff sign-in in the web view too: the page
  hands the app only the Stripe connection token, never the staff token.
- No Face ID lock yet. The app holds a full staff session, the same as the
  home-screen web app. The charge authorization lives in the handoff token
  (60-second TTL, one-time use).
- Links to other sites, phone numbers and maps open outside the app;
  `window.open` pages from the portal open in an in-app sheet that shares
  the sign-in.

## Troubleshooting

- **`./bootstrap.sh` fails with "xcodegen: command not found"** — Homebrew
  install silently failed. Run `brew install xcodegen` manually and
  re-run the script.
- **"No tap-to-pay reader found"** during discovery — most likely cause:
  the entitlement isn't applied to this build, or the app is running in
  the simulator. Confirm on a real device; in Signing & Capabilities
  verify the proximity-reader entitlement is listed.
- **"Tap to Pay did not start on this iPhone"** — discovery ended with no
  reader and no error, or gave no answer in 30 seconds
  (`TerminalManager.discoverFirstReader`). Tap Try again. If it repeats,
  run the reader-found checks in the line above.
- **"This payment timed out"** — the 15-minute terminal token expired
  (the amount screen sat open). Close it and tap Tap to Pay again.
- **410 `replay` on `/validate-handoff`** — the token was already used.
  The portal's Charge now button needs to mint a fresh handoff.
- **409 `invoice_amount_changed`** — admin edited the invoice total
  between mint and validate. Close the flow and re-tap Charge now.

## What's intentionally NOT here (future work)

- A full receipt inside the app. The success screen shows the amount
  charged and the card; the portal's own receipt email and SMS do the rest.
- Manual PaymentIntent retrieval / retry UI. If the NFC flow errors out,
  the tech re-handoffs — simpler than maintaining an iOS-side retry
  state machine.
- Background reader keep-alive. The SDK disconnects when the app is
  backgrounded and reconnects by itself when it comes back; the app
  connects again if that fails.
- A custom launch screen.
