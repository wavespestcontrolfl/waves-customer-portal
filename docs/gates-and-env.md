# Gates and environment variables (Railway)

One entry per documented `GATE_*` flag or env var family (not every variable has a paragraph, but every `GATE_*` the code reads has a line in the generated index at the end of this file): its default, where it is read, what on and off do, and how to kill it. Moved out of `CLAUDE.md` so it is read on demand instead of loading into every session.

Look a variable up by name (`grep -n 'GATE_NAME' docs/gates-and-env.md`); each entry is one paragraph on one line. Add or change an entry in the same PR that adds or changes the variable.

Inventory agent (dark): `GATE_INVENTORY_AGENT` — **ships DARK: off unless exactly `true`**, read at call time (`server/services/purchase-receipts/inventory-agent.js`; unset = kill, no redeploy). Requires `GATE_PURCHASE_RECEIPT_RESTOCK` ALSO on and a valid, offset-bearing `PURCHASE_RECEIPT_SINCE` — with either missing, the agent does nothing (`skipped: 'no_since'`/`'gated'`) exactly like the deterministic receipt sweep it rides behind. On, it resolves a `purchase_receipt_lines` row the deterministic sweep could only hand off (`agent_pending`: unmatched / needs_size / size_mismatch) with one bounded LLM call per line, then validates every number the model proposes against the purchased title in plain code before writing anything (`validateReading` / `validateExisting` / `validateNewProduct`) and applies in one transaction. Read fresh on every 15-minute scheduler tick (`server/services/scheduler.js`), right after the deterministic sweep — no redeploy needed to flip it. Kill behavior: unsetting the gate does NOT strand queued lines — the same scheduler tick calls `drainAgentQueue` instead, which restores every `agent_pending` line to the status it would have held WITHOUT the agent (its recorded `handoffFrom`, or `unmatched` when that's missing), ringing the same "not added" bell the deterministic sweep would have for `needs_size`/`size_mismatch`. Undo one agent-logged line (reverses the stock movement, restores an EXISTING product's container_size/inventory_unit/inventory_on_hand/default_unit, deletes an agent-created alias, never deactivates an agent-created product): `railway run --service Postgres node ops/agents/inventory-agent-undo.js --line=<id|8-char-prefix>` (dry run; add `--execute` to apply) — refuses when the product row or anything referencing it (a service's COGS mapping, a visit's applied product, a protocol, a restock request, …) changed since the agent's decision.

Ships dark. `EDITORIAL_REVIEW_PRIVATE_KEY` (Ed25519 PEM/base64 DER) is restricted to the publisher/trusted reviewer; `EDITORIAL_REVIEW_PUBLIC_KEY` is shared with Astro validation. Voice relay manual eval: `npm run eval:voice-relay` runs the synthetic fixture through Sandy's live conversation loop in a dedicated CLI process, with deterministic grading and refused conversation database access. Requires `ANTHROPIC_API_KEY`; `--only=<id,...>` selects scenarios and `--fixture=<path>` supplies a custom fixture. Optional `--judge` grades completed transcripts through `TEXT_POLICIES.voiceJudge` (`MODEL_VOICE_JUDGE` pins the Anthropic primary; the registered OpenAI fallback is advisory). Judge calls may write ordinary LLM ledger/trace rows when their gates are on. Manual runs retry a failed scenario set once and send no notifications unless `--notify` is present. `GATE_VOICE_RELAY_EVAL` explicitly opts in (all environments) to Monday 03:50 America/New_York, under the existing exclusive cron lock and in a child process with `--judge --notify`; default off. Repeated failures or an inconclusive run use the existing admin regression bell and ops digest/email, controlled by `EVAL_REGRESSION_EMAIL` (`off` disables the email/digest channel). Rubric and fixture contracts: `docs/voice-quality-rubric.md`.

Lawn actuals ledger: `GATE_LAWN_ACTUALS_LEDGER` — **ships DARK: off unless exactly `true`**, read at call time. On, every lawn closeout (member, one-time, commercial, and an incomplete visit that applied product) writes its `lawn_protocol_service_completions` + `lawn_protocol_product_actuals` rows with the frozen `property_id`, each product's own treated area / zones / method, removed plan defaults as `skipped` rows (no reason demanded), and protocol attribution ONLY when a WaveGuard tier or an explicit appointment assignment applies, the saved turf profile proves THIS service property, AND the built plan resolved that assignment (`lawnPlanAttributesVisit`; `metadata.attribution` = `protocol` / `none` — a track-resolved protocol is never stamped on a one-time visit, and an explicitly assigned visit records `none` rather than a calendar-resolved protocol when `GATE_LAWN_COMPLETION_DEFAULTS` is off, so run the ledger gate with the defaults gates). Command Center protocol counts read protocol-attributed rows only either way.

Multiple discounts per service: `GATE_DISCOUNT_STACKING` — **ships DARK: off unless exactly `true`**, read at call time via `discountStackingLive()` (`server/config/feature-gates.js`) — the canonical reader; the `gates.discountStacking` map entry is for `logGateStatus` only and must never be read directly for a live decision. The one stacking rule (owner ruling 2026-09-11, "the lesser of the two") lives in `server/services/discount-stack.js`: dollar credits come off first, then percentages compound on what is left (10% then 5% off $111 is $16.10, never an additive $16.65), with EVERY discount-carrying surface reading the same gate together — schedule creation/extension (`server/routes/admin-schedule.js`), and invoice/document calculation: `InvoiceService.create`, the existing-draft edit/retotal path (`calculateUpdateFinancials`), and discount-engine.js's `/api/admin/discounts/calculate` preview all flip to `discountStackingLive()` in the same change, so preview and save can never disagree ($111 at 10%+5% previews AND saves $16.10 either way — no half-migrated state where only one side compounds). `GET /api/admin/discounts/stacking` calls `discountStackingLive()` and reports it for a picker to read. The corrected cent-exact rounding (5% of $20.70 is $1.04, never the old float formula's $1.03) is live regardless of the gate. Invoice document-stack specifics (server/services/invoice.js): an unparented negative line item — a stored stamp (`scheduled_service` / `validated_checkout` / the builder's own "Scheduled price adjustment" reconciliation row) OR a plain literal credit with no `discount_id` — always joins the document stack, reducing the base a fresh percentage compounds against; a scheduled appointment discount's service-key/category scope (`scheduled_services.discount_service_key_filter` / `_category_filter`) narrows its document term to the line(s) it reaches, with "no service-key snapshot anywhere on this invoice ⇒ unscoped" (pre-lane invoices) and "a snapshot present but matching no line ⇒ the credit resolves to $0" (orphaned, never a silent overcharge replay of a frozen amount). Gate off keeps every one of these paths byte-identical to before this lane, in its own untouched branch. `slot-reservation.js` carries no discount arithmetic.

First-touch auto-release: `GATE_FIRST_TOUCH_AUTO_RELEASE` — **ships DARK: off unless exactly `true`**, layered on `GATE_TRIAGE_AUTO_RESOLVE` + `GATE_TRIAGE_AUTO_RESOLVE_EVIDENCE`. On, an open `email_unverified` card whose dictation was unambiguous — no arbiter doubt, V1 + V2 + the release target agree, one candidate ≥ 0.9, no `name_email_mismatch`, the domain has MX, the pending hold targets that exact address, card younger than `FIRST_TOUCH_AUTO_RELEASE_MAX_AGE_DAYS` (default 7) — auto-resolves (`email_dictation_unambiguous`), and the ledger sweep then releases the hold: the new-lead drip and newsletter opt-in go out. Sends customer email — owner-flip only. The gate is re-asked at the send: a card the resolver closed under it approves a release only while the gate is still on (flip it off and queued auto-releases stop), and every release re-checks the hold's customer binding, the customer's liveness, and address ownership under the hold's row lock. Independent of the gate: the ledger sweep retires any pending hold older than `FIRST_TOUCH_HOLD_MAX_AGE_DAYS` (default 14) as `blocked` / `first_touch_stale` — a first touch weeks late is never sent.
First-touch hold shelf life: `FIRST_TOUCH_HOLD_MAX_AGE_DAYS` (default 14). The ledger release engine retires any held first-touch send whose hold OR source call is older than this as `blocked` / `first_touch_stale` — on the canonical claim path every release takes and in the ledger sweep's pre-pass — so a "welcome, new lead" email is never sent weeks late. An unreadable source-call age re-pends the hold (`call_age_unavailable`) rather than passing.

Content publish gates: `GATE_COMPLIANCE` — the semantic compliance gate, an LLM second layer for `REENTRY_SAFETY_CLAIM` / `BANNED_TOPIC` catching the paraphrases regex cannot express. **Ships DARK: off unless set to exactly `true`.** It P0-blocks a publish, so calibrate before enabling — `node ops/agents/compliance-gate-eval.js --document --all` (live API keys required) reports recall/precision over the labelled corpus 23 Codex rounds produced. **`--document` is required for an activation decision**: without it the harness sends isolated sentences, which measures discrimination but not long-document recall or whether a banned topic reads as offered-by-Waves vs merely discussed — the context production always supplies. - `GATE_VISIT_PREP_READ_SWEEP` — `server/config/feature-gates.js` — visit-prep read recovery sweep, dark. Every 15 minutes (scheduler.js, checked BEFORE the cron lock, so off = no query, no write) it re-runs the same dispatchVisitPrepRead (services/visit-prep-read-dispatch.js, which runs only live engines) for at most 10 submissions from the last 14 ET days on still-upcoming, join-eligible visits: read_status 'none' older than 15 minutes (never attempted: photo load failed, claim error, stop moved), 'unsupported' where a live engine now reads the stop, and a 'done' or 'failed' read made by the wrong engine or subject for the stop as it is now (released to 'none', then re-read; a row checked and needing nothing is skipped for an hour). A batch with failed retries fails the job run (job_health).
