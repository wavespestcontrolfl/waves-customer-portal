# Reviewed human email corpus

This implements source `email_human_reply` from scope #4215. It extends the
existing nightly voice-corpus miner and its `(source, source_id)` insert-ignore
key. It creates no Gmail drafts, sends no messages, and calls no model.

Gmail `SENT` and `auto_action=outbound_skipped` do not prove human authorship.
The current send paths do not retain that distinction. An authorized operator
must review historical replies and attest that the selected text was written
by a person, rather than generated by AI or taken from an automated template.
The miner does not infer authorship from a shared mailbox or missing automation
metadata. No historical replies were approved or mined as part of development.

The email source requires both:

- `GATE_VOICE_CORPUS_EMAIL_SOURCE=true` (default false in every environment).
  The existing nightly job also requires `GATE_VOICE_CORPUS_MINER` in production.
- A JSON value in the existing `system_settings` key
  `email_voice_corpus_selection`, populated through the authorized settings
  workflow after review. No new approval workflow or schema is introduced.

The value has this shape; IDs below are placeholders, not a usable selection:

```json
{
  "version": 1,
  "reviewedBy": "<reviewing admin UUID>",
  "reviewedAt": "<ISO timestamp with UTC offset>",
  "replyIds": ["<reviewed emails.id UUID>"],
  "heldOutCustomerIds": ["<evaluation customer UUID>"],
  "heldOutThreadIds": ["<evaluation Gmail thread ID>"]
}
```

All three arrays are required, including explicitly empty holdout arrays.
Each is bounded to 500 entries. Finalize the evaluation split before mining;
exclude the whole customer or thread, not just its answer message.
`reviewedBy` identifies the reviewer, not the author: corpus `admin_user_id`
stays null. Review attribution, inbound ID, and Gmail thread ID are retained
in the corpus outcome metadata without raw message text.

The nightly email pass considers reviewed replies from the last 90 days.
SMS and call lookbacks keep their existing behavior. The selected reply must
belong to the configured `GMAIL_USER_EMAIL` mailbox (default
`contact@wavespestcontrol.com`) and one uniquely matched active customer.
Known outreach threads, operational mail, conflicting identities, and
ambiguous pairing are excluded. The preceding inbound must be authenticated;
an intervening sent message prevents reusing an already answered inbound.
HTML is converted, quoted history and signature tails are stripped, PII and
access codes are redacted, and prompt-control examples are rejected. Intent
comes from the existing SMS intent classifier.

Missing/invalid selection, a disabled gate, or an unavailable email source
skips email mining. The summary reports counts and reasons, never raw bodies.
Existing SMS examples and shared voice-profile inputs stay source-filtered;
email rows cannot trigger a shared profile refresh.

`email/email-reply-style.js` provides the shared drafter's style reader. It
checks the source gate and current reviewed selection on every fetch, excludes
the current customer's examples and held-out identities/threads, and returns
at most four clean email pairs for the inbound intent. Removing an ID withdraws
it immediately even though the existing corpus row remains. Current source
email ownership/thread are checked too, so reassignment withdraws the old row.
Missing examples
fall back to the existing SMS reader, including its sealed-evaluation exclusion
and exclusion of the current customer. Read failures remain distinguishable
from an empty corpus, including outside transactions.
Examples are untrusted USER-channel style data, never customer facts.

`GATE_EMAIL_VOICE_PROFILE=false` is a separate, strict opt-in. When enabled,
the reader loads only the current approved shared profile, strips factual and
prompt-control lines through the existing profile sanitizer, and returns its
ID/version. Revocation takes effect on the next read. Optional reads use
savepoints so a schema failure does not abort a caller's transaction.

The reader adds no runtime caller or Gmail side effect. Both drafting entry
points retain their existing behavior until the separate shared-generator
integration lands.

Verification uses fictional records in an isolated development PostgreSQL
database, with transaction rollback. Run `tests/email-voice-corpus-db.test.js`
through Jest from `server/` with that test database selected. Unit coverage is
in `tests/email-voice-corpus-miner.test.js`; existing SMS miner and voice-profile
tests protect their unchanged behavior.

Reader coverage is in `tests/email-reply-style-db.test.js`: current-selection
revocation, customer/thread holdouts, SMS fallback, schema failure, injection,
and approved-profile gating/revocation, using synthetic transaction fixtures.
