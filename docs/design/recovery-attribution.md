# Recovery attribution follow-up to PR #4437

Status: design proposal; implementation is separate from the safety change.

Persist the recovery result with the call processing result. Triage cards remain operator tasks; their status, timestamps, and payload edits must not establish a promotion cohort.

## Deployment epoch and executed provenance

Two identities are recorded, and they serve different questions.

The **deployment epoch** answers "which pipeline is deployed". It is one composite hash over the full contract set a deployment can execute, computed from configuration and code at startup, identical for every generation processed on that deployment regardless of the path a call takes. The set is: the primary transcription provider and model with its executed prompt and keyword hints (`OPENAI_TRANSCRIPTION_PROMPT` and the vocabulary hints when the model is promptable); the fallback transcription provider and model; the speaker-relabeling model and prompt (`labelTranscriptWithOpenAI`, which rewrites speaker attribution before `buildDecoderPrompt` consumes the primary transcript); the V1 and V2 extraction models and prompts that produce the street and locality handed to `recoverStreetAddress`; the contact-pass transcription model and the `CONTACT_DICTATION_TRANSCRIPTION_PROMPT` version; the contact-decoder model and prompt version; the recovery module's own prompt version and resolved model for each recovery method (autocomplete, dictation, phonetic); and an explicit `RECOVERY_POLICY_VERSION` constant. That constant versions the deterministic recovery implementation itself: `RECOVERABLE_STATUSES`, candidate ordering and limits, `confirmPrediction`, uniqueness checks, and decoder sanitization. Any change to that behavior must bump the constant, and a new epoch always requires a new activation (below). Eligibility for the cohort is decided by the deployment epoch alone.

The **executed provenance** answers "what actually produced this generation". Every transcript artifact records the contract that produced it (provider, model, executed prompt and hints, fresh or cached), and each processing generation stores the set of producing contracts for the artifacts it consumed together with the relabeling, extraction, decoder, and recovery contracts it executed. This is path-specific by design: the contact pass is conditional, an autocomplete success never executes the phonetic model, fallback transcription uses another provider, and a skipped recovery executes no recovery contract. Provenance is never hashed into the epoch, so those paths do not fragment the cohort.

Provenance still gates eligibility one way: a generation is admissible only when every contract identity in its executed provenance is a member of the current deployment epoch's contract set. Reprocessing that reuses a cached transcript, or that falls back to a stored transcript after a fresh transcription failure, carries the older transcription contract in its provenance; that identity is absent from the current set, so the generation is excluded even though its epoch is current. When any artifact's provenance is missing, the generation is unattributable: it is stamped with a null epoch, excluded from the cohort, and counted.

## Attribution records

Attribution is append-only. Each finalized processing generation writes its own immutable attribution record, keyed by call and generation, rather than overwriting a single value on call_log: the deployment epoch, the executed provenance, the execution timestamp, the processing generation, whether recovery was attempted or skipped, and for attempted rows the recovery method, the individual contract identities that produced candidates for that method, and the recovered/failed outcome. Skipped generations are recorded with the same epoch. Claiming a new generation never clears or edits an earlier record. Capture every identity at execution, not when a later card is filed. Store only contract identity and outcome, without candidate streets or transcript text.

The attribution insert and the terminal routing-result update commit in **one transaction**. The transaction inserts the attribution row, applies the `processing_token`-guarded terminal update to the routing result, and advances the call's current-generation pointer; when the guarded terminal update affects zero rows, the transaction rolls back all three, so a lost claim leaves neither an orphaned attribution row nor a finalized result without one. A shared `processing_token` predicate on two separate statements is not an acceptable substitute. Interrupted, unprocessed, legacy, or generation-mismatched records are unattributable and excluded with explicit counts. A skipped result is current only when it belongs to the finalized processing generation; absence must never mean skipped. Preserve compatibility for older deployed workers: missing attribution cannot produce a positive readiness verdict.

## Activation ledger and cohort boundary

The cohort boundary comes from a durable activation ledger, not from the attribution records. Each deployment whose deployment epoch differs from the ledger's latest row appends a row with the new epoch and its activation timestamp; the ledger is append-only and never rewritten by reprocessing.

The readiness command computes its own deployment epoch from the checkout and environment it runs in, then reads the **latest activation row overall**, not the newest row for its computed epoch. If the latest row's epoch differs from the command's epoch, the command fails closed and reports both epochs: a stale checkout or environment running epoch A cannot select A's historical activation and pass on a historical sample while production runs B. Only when the latest row matches does its timestamp become the boundary. The command admits attribution records whose epoch equals the current epoch, whose provenance is admissible, and whose execution timestamp is at or after that activation. After an A → B → A rollback the second A row is the latest row and is newer than every pre-B record, so pre-B successes are excluded even if every B-era call is later reprocessed under A, even if the B interval attempted no recovery, and regardless of any older foreign epoch that remains. `--since <ISO date>` narrows the cohort further but can never widen it past the activation. When the ledger is empty the command fails closed and says so; the derived contiguous-run boundary in `scripts/v2-promotion-readiness.js` is not used here.

## Readiness query

The readiness command reads the attribution records directly and counts **each call once**. It joins the attribution table to the call's current finalized-generation pointer and admits only the record for that generation; superseded generations remain in the table for audit but never qualify. A force-reprocessed call therefore contributes exactly one outcome, the current one, and repeated reprocessing can neither inflate the minimum sample nor keep a superseded success alive. Attempted records in the cohort qualify only by their epoch, provenance, and outcome. A recovered result reconstructs an accepting address verdict only for that same finalized processing result. A failed result keeps its failure verdict. Triage card creation, resolution, reopening, and timestamp changes have no effect on the cohort.

## Regression matrix

Restore the readiness command only after database tests prove: success → failure → success on one call, asserting that only the final success contributes and the sample counts one call; failed → skipped → failed; prompt changes; model changes and rollbacks, including A → B → A with pre-B samples excluded, the same sequence where every B-interval generation is a skipped recovery, and the same sequence where every B-era call is reprocessed under restored A while an older foreign epoch remains; a primary transcription prompt or hint change with provider and model unchanged; a relabeling prompt or model change with every other contract unchanged; a V1 or V2 extraction prompt or model change with every other contract unchanged; a `RECOVERY_POLICY_VERSION` bump with every model and prompt unchanged; a cached or fallback transcript consumed after a transcription-contract change; two current-epoch generations that took different paths (contact pass skipped, autocomplete success without the phonetic model, fallback provider) and both qualify; an artifact without provenance; a contact-pass transcription prompt change that leaves the decoder and recovery pairs unchanged; a contact-decoder prompt or model change that leaves the recovery pair unchanged; an empty ledger; a command whose computed epoch is older than the latest activation row; stale worker after claim loss, including a guarded terminal update of zero rows rolling back the attribution insert; crashes between extraction, recovery, routing, and finalization; historical rows without attribution; and operator mutations of all related cards.

The original experimental implementation is retained in commit 6016932fc on PR #4437 for investigation. It is reference material, not the implementation proposed here.
