# Recovery attribution follow-up to PR #4437

Status: design proposal; implementation is separate from the safety change.

Persist the recovery result with the call processing result. Triage cards remain operator tasks; their status, timestamps, and payload edits must not establish a promotion cohort.

## Deployment epoch and executed provenance

Two identities are recorded, and they serve different questions.

The **deployment epoch** answers "which pipeline produced this generation". It is not a hand-maintained list of prompts and models: every earlier revision of this proposal enumerated contracts and every review found one missing (the fallback prompt, the relabeling pass, the extraction prompts, the kill switch). The epoch is instead closed by construction from three components, each of which is complete over its domain:

1. **Pipeline build identity**: a hash of the git tree objects of the call pipeline's source set, not the whole deployed commit. The set is the transitive module graph reached from the processing entry points (`call-recording-processor.js`, `contact-dictation.js`, `address-validation/recovery.js` and what they import), resolved at build time and recorded with the epoch. Every inline prompt (including the Gemini fallback transcription instructions), every prompt version constant, the relabeling and V1/V2 extraction prompt templates, and the deterministic recovery implementation (`RECOVERABLE_STATUSES`, candidate ordering and limits, `confirmPrediction`, uniqueness checks, decoder sanitization) live in that set, so any change to any of them changes this component without anyone remembering to list it, while a client, documentation, billing, or infrastructure commit that touches nothing in the set leaves it unchanged and does not reset the cohort.
2. **Configuration snapshot**: a hash over the values of the behavior-affecting environment keys the call pipeline reads, taken from one registry module that the pipeline modules import to read their configuration. A module cannot read a key without registering it, and each registration declares the key as behavior or credential; only behavior keys are hashed, so rotating an API credential does not change the epoch, while provider and model selection for every transcription path, `OPENAI_TRANSCRIPTION_PROMPT`, `CONTACT_DICTATION_TRANSCRIPTION_PROMPT`, the decoder and recovery model settings, and gates such as `ADDRESS_RECOVERY_ENABLED` do. Turning recovery off therefore yields a different epoch, and pre-disable successes cannot support a verdict for a pipeline that never runs recovery. A test asserts that every key the pipeline reads is registered and that every registered key carries a classification.
3. **Live catalog identity**: a hash of the bookable-catalog rows from which the extraction prompt is derived on each call. The extraction contract is not fixed for a deployment because that catalog is reloaded per call, so the catalog hash is computed at the same point the prompt is derived and is part of the epoch of that generation.

The epoch is computed **per processing generation at execution time**, not at process startup, so a catalog edit changes the epoch of the next generation without a restart. It is still identical for every generation processed on the same build, configuration, and catalog regardless of the path a call takes: the components are properties of the deployment, not of what the call executed. Eligibility for the cohort is decided by epoch equality alone.

The **executed provenance** answers "what actually produced this generation". Every transcript artifact records the epoch components under which it was produced (build, configuration snapshot, catalog identity) together with the provider, model, executed prompt hash and hints, fresh or cached. Each processing generation stores the provenance of the artifacts it consumed together with the relabeling, extraction, decoder, and recovery contracts it executed. This is path-specific by design: the contact pass is conditional, an autocomplete success never executes the phonetic model, fallback transcription uses another provider and its own inline prompt, and a skipped recovery executes no recovery contract. Provenance is never hashed into the epoch, so those paths do not fragment the cohort.

Provenance still gates eligibility one way: a generation is admissible only when every artifact it consumed was produced under the generation's own epoch components. Reprocessing that reuses a cached transcript, or that falls back to a stored transcript after a fresh transcription failure, carries an artifact produced under an older build or configuration; that artifact's recorded components differ from the generation's, so the generation is excluded even though its own epoch is current. When any artifact's provenance is missing, the generation is unattributable: it is stamped with a null epoch, excluded from the cohort, and counted.

## Attribution records

Attribution is append-only. Each finalized processing generation writes its own immutable attribution record, keyed by call and generation, rather than overwriting a single value on call_log: the deployment epoch, the executed provenance, the execution timestamp, the processing generation, whether recovery was attempted or skipped, and for attempted rows the recovery method, the individual contract identities that produced candidates for that method, and the recovered/failed outcome. Skipped generations are recorded with the same epoch. Claiming a new generation never clears or edits an earlier record. Capture every identity at execution, not when a later card is filed. Store only contract identity and outcome, without candidate streets or transcript text.

The attribution insert and the terminal routing-result update commit in **one transaction**. The transaction inserts the attribution row, applies the `processing_token`-guarded terminal update to the routing result, and advances the call's current-generation pointer; when the guarded terminal update affects zero rows, the transaction rolls back all three, so a lost claim leaves neither an orphaned attribution row nor a finalized result without one. A shared `processing_token` predicate on two separate statements is not an acceptable substitute. Interrupted, unprocessed, legacy, or generation-mismatched records are unattributable and excluded with explicit counts. A skipped result is current only when it belongs to the finalized processing generation; absence must never mean skipped. Preserve compatibility for older deployed workers: missing attribution cannot produce a positive readiness verdict.

## Activation ledger and cohort boundary

The cohort boundary comes from a durable activation ledger, not from the attribution records. The ledger is append-only and never rewritten by reprocessing. Rows are appended **on first observation, by the workers themselves**, not at process startup: when a worker finalizes a generation whose epoch differs from the ledger's latest row, the finalizing transaction appends a row for its epoch. Appends are serialized by a ledger-wide transaction advisory lock (`pg_advisory_xact_lock` on one constant key) taken before the latest-row read, so two workers finalizing the first generations of a new epoch concurrently cannot both observe the old latest row and both append; the second waits, re-reads, sees its own epoch as latest, and appends nothing. The advisory lock also covers the initially empty ledger, so no sentinel row is needed, and it orders concurrent different-epoch appends by the order their finalizations actually committed. Because activation is driven by the generations actually being produced, it tracks the deployment that is really processing calls. A B canary that appends its row and is then terminated while A pods keep serving is followed by the next A generation, which observes that the latest row is B and appends a fresh A row, so B stops being latest without anyone restarting A, and the new A row is newer than every pre-B record. A catalog edit appends a row from the first generation that derives the new extraction prompt.

A fleet that is genuinely mixed (A and B both finalizing) appends alternating rows and keeps moving the boundary forward. That is the intended fail-safe direction: the cohort shrinks to nothing rather than admitting evidence from a pipeline that is not the only one live. The readiness command makes that explicit by failing closed when any attribution record with a different epoch has an execution timestamp at or after the boundary.

The readiness command computes its own epoch from the checkout, environment, and current catalog it runs against, then reads the **latest activation row overall**, not the newest row for its computed epoch. If the latest row's epoch differs from the command's epoch, the command fails closed and reports both epochs: a stale checkout or environment running epoch A cannot select A's historical activation and pass on a historical sample while production runs B. Only when the latest row matches does its timestamp become the boundary. The command admits attribution records whose epoch equals the current epoch, whose provenance is admissible, and whose execution timestamp is at or after that activation. After an A → B → A rollback the second A row is the latest row and is newer than every pre-B record, so pre-B successes are excluded even if every B-era call is later reprocessed under A, even if the B interval attempted no recovery, and regardless of any older foreign epoch that remains. `--since <ISO date>` narrows the cohort further but can never widen it past the activation. When the ledger is empty the command fails closed and says so; the derived contiguous-run boundary in `scripts/v2-promotion-readiness.js` is not used here.

The whole readiness read is fenced against concurrent activation. It runs in one `REPEATABLE READ` transaction, so the latest-row read and the cohort query see the same snapshot; after the cohort is gathered it re-reads the latest activation row outside that snapshot and fails closed if the row has changed. It also recomputes the catalog-derived epoch component from the live catalog outside the snapshot and fails closed if it differs from the epoch it started with, because a catalog edit that lands during the read changes the extraction contract of the next call before any worker has finalized a generation that would append an activation. A B activation that lands while an A verdict is being computed, or a catalog edit that lands before the first new-epoch generation finalizes, therefore cannot be followed by a positive A verdict.

## Readiness query

The readiness command reads the attribution records directly and counts **each call once**. It joins the attribution table to the call's current finalized-generation pointer and admits only the record for that generation; superseded generations remain in the table for audit but never qualify. A force-reprocessed call therefore contributes exactly one outcome, the current one, and repeated reprocessing can neither inflate the minimum sample nor keep a superseded success alive. Attempted records in the cohort qualify only by their epoch, provenance, and outcome. A recovered result reconstructs an accepting address verdict only for that same finalized processing result. A failed result keeps its failure verdict. Triage card creation, resolution, reopening, and timestamp changes have no effect on the cohort.

## Regression matrix

Restore the readiness command only after database tests prove: success → failure → success on one call, asserting that only the final success contributes and the sample counts one call; failed → skipped → failed; prompt changes; model changes and rollbacks, including A → B → A with pre-B samples excluded, the same sequence where every B-interval generation is a skipped recovery, and the same sequence where every B-era call is reprocessed under restored A while an older foreign epoch remains; a primary transcription prompt or hint change with provider and model unchanged; a relabeling prompt or model change with every other contract unchanged; a V1 or V2 extraction prompt or model change with every other contract unchanged; a deterministic recovery-behavior change with every model and prompt unchanged (build identity differs); a fallback transcription prompt change with the fallback provider and model unchanged; a bookable-catalog edit with no restart, activating a new epoch from the next generation; `ADDRESS_RECOVERY_ENABLED` flipped to false with nothing else changed, excluding every pre-disable success; a configuration key read without registration, failing the registry test; a cached or fallback transcript consumed after a transcription-contract change; two current-epoch generations that took different paths (contact pass skipped, autocomplete success without the phonetic model, fallback provider) and both qualify; an artifact without provenance; a contact-pass transcription prompt change that leaves the decoder and recovery pairs unchanged; a contact-decoder prompt or model change that leaves the recovery pair unchanged; an empty ledger; a command whose computed epoch is older than the latest activation row; a B canary that activates and then stops while A keeps processing, with the next A generation restoring A as latest and pre-B A evidence excluded; a mixed fleet with both epochs finalizing after the boundary, failing closed; a B activation appended between the command's latest-row read and its cohort query, failing closed on the re-read; a catalog edit during readiness before the first new-epoch generation finalizes, failing closed on the catalog recheck; two workers finalizing the first generations of a new epoch concurrently, appending exactly one row; an unrelated client or documentation deploy and an API credential rotation, each leaving the epoch and cohort unchanged; stale worker after claim loss, including a guarded terminal update of zero rows rolling back the attribution insert; crashes between extraction, recovery, routing, and finalization; historical rows without attribution; and operator mutations of all related cards.

The original experimental implementation is retained in commit 6016932fc on PR #4437 for investigation. It is reference material, not the implementation proposed here.

## Open design constraints from review (2026-09-22, round 7, not yet resolved)

Two further constraints were raised after the epoch was scoped to the pipeline source set. They are recorded so the implementation addresses them; the proposal above has not been rewritten to satisfy them.

1. The pipeline source set is still too wide: `call-recording-processor.js` was a 17,598-line end-to-end orchestrator as of the 2026-09-22 review (20,145 lines as of 2026-09-26) whose transitive imports reach notification, Stripe, scheduling, and appointment modules, so an unrelated edit or comment inside that graph changes the epoch and discards the 100-call cohort. The hash must cover only the source slice that can affect transcription, extraction, or recovery, which in practice means extracting that slice into its own modules before the epoch can be computed from code; a test must show an unrelated edit inside the orchestrator leaves the epoch unchanged.
2. Credential presence is a second kill switch: when the Google credentials are absent, `address-validation/index.js` returns `not_attempted` and recovery never runs, yet the epoch is unchanged because credential values are excluded. Hash a non-secret provider-availability bit (present or absent) for each credential-classified key while continuing to exclude the value, and cover present → absent transitions in the regression matrix.
