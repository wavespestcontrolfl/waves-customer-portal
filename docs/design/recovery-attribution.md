# Recovery attribution follow-up to PR #4437

Status: design proposal; implementation is separate from the safety change.

Persist the recovery result with the call processing result. Triage cards remain operator tasks; their status, timestamps, and payload edits must not establish a promotion cohort.

Define the recovery contract as the full set of prompts, models, and hints that can shape a recovery candidate on the current deployment, whichever path a given call takes: the primary transcription provider and model together with its executed prompt and keyword hints (`OPENAI_TRANSCRIPTION_PROMPT` and the vocabulary hints when the model is promptable), the contact-pass transcription model and the `CONTACT_DICTATION_TRANSCRIPTION_PROMPT` version, the contact-decoder model and prompt version, and the recovery module's own prompt version and resolved model. The decoder consumes both the primary and the contact-pass transcripts (`contact-dictation.js` `buildDecoderPrompt`), so a change to either transcription contract changes the street alternatives even when the decoder and recovery pairs are unchanged. The contract epoch is one composite hash over all of these identities.

The epoch is not computed from configuration alone. Every transcript artifact records the contract that actually produced it (provider, model, executed prompt and hints, fresh or cached), and the epoch of a processing generation hashes the producing contract of the artifacts it consumed together with the decoder and recovery contracts it executed. Reprocessing that reuses a cached transcript, or that falls back to a stored transcript after a fresh transcription failure, therefore carries the older transcription contract in its epoch and cannot match the current one. When an artifact's provenance is missing, the generation is unattributable: it is stamped with a null epoch, excluded from the cohort, and counted.

Attribution is append-only. Each finalized processing generation writes its own immutable attribution record, keyed by call and generation, rather than overwriting a single value on call_log: the epoch, the execution timestamp, the processing generation, whether recovery was attempted or skipped, and for attempted rows the recovery method (autocomplete, dictation, phonetic), the individual contract identities that produced candidates for that method, and the recovered/failed outcome. Skipped generations are recorded with the same epoch. Claiming a new generation never clears or edits an earlier record; the routing result continues to point at the generation that is current for the call. Capture every identity at execution, not when a later card is filed. Store only contract identity and outcome, without candidate streets or transcript text.

Finalize the record under the same processing_token guard as the routing result. Interrupted, unprocessed, legacy, or generation-mismatched records are unattributable and excluded with explicit counts. A skipped result is current only when it belongs to the finalized processing generation; absence must never mean skipped. Preserve compatibility for older deployed workers: missing attribution cannot produce a positive readiness verdict.

The cohort boundary comes from a durable activation ledger, not from the attribution records. Each deployment that changes any contract identity appends a row with the new epoch and its activation timestamp; the ledger is append-only and never rewritten by reprocessing. The readiness command reads the newest ledger row for the current epoch and admits only attribution records whose epoch equals the current epoch and whose execution timestamp is at or after that activation. After an A → B → A rollback the second A row is newer than every pre-B record, so pre-B successes are excluded even if every B-era call is later reprocessed under A, even if the B interval attempted no recovery, and regardless of any older foreign epoch that remains. `--since <ISO date>` narrows the cohort further but can never widen it past the activation. When the ledger has no row for the current epoch the command fails closed and says so instead of returning a verdict; the derived contiguous-run boundary in `scripts/v2-promotion-readiness.js` is not used here.

The readiness command reads the attribution records directly. Attempted records in the cohort qualify only by their epoch and outcome. A recovered result reconstructs an accepting address verdict only for that same finalized processing result. A failed result keeps its failure verdict. Triage card creation, resolution, reopening, and timestamp changes have no effect on the cohort.

Restore the readiness command only after database tests prove: success → failure → success; failed → skipped → failed; prompt changes; model changes and rollbacks, including A → B → A with pre-B samples excluded, the same sequence where every B-interval generation is a skipped recovery, and the same sequence where every B-era call is reprocessed under restored A while an older foreign epoch remains; a primary transcription prompt or hint change with provider and model unchanged; a cached or fallback transcript consumed after a transcription-contract change; an artifact without provenance; a contact-pass transcription prompt change that leaves the decoder and recovery pairs unchanged; a contact-decoder prompt or model change that leaves the recovery pair unchanged; a current epoch with no ledger row; stale worker after claim loss; crashes between extraction, recovery, routing, and finalization; historical rows without attribution; and operator mutations of all related cards.

The original experimental implementation is retained in commit 6016932fc on PR #4437 for investigation. It is reference material, not the implementation proposed here.

## Open design constraints from review (2026-09-21, round 4, not yet resolved)

Codex review of this proposal raised six further constraints after the activation-ledger revision. They are recorded here so the implementation addresses them; the proposal above has not yet been rewritten to satisfy them.

1. Eligibility must use one stable deployment epoch. Per-generation hashes over only the contracts a call consumed vary within one deployment (conditional contact pass, autocomplete successes that never run the phonetic model, fallback providers, skipped recoveries), so path-specific executed provenance must be stored separately from the deployment epoch used for eligibility.
2. The epoch must also cover the speaker-relabeling contract (`labelTranscriptWithOpenAI`) and the V1/V2 extraction contracts that produce the street and locality handed to `recoverStreetAddress`.
3. The epoch must include an explicit version for the deterministic recovery implementation (`RECOVERABLE_STATUSES`, candidate ordering and limits, `confirmPrediction`, uniqueness checks, decoder sanitization), with a new activation whenever that behavior changes.
4. Readiness must count each call once, joining attribution to the call's current finalized-generation pointer, so repeated reprocessing cannot inflate the sample or retain superseded outcomes; the success → failure → success test must assert only the final success counts.
5. The command must read the latest activation row overall and fail closed unless its epoch matches the command's contract, so a stale checkout cannot pass on a historical sample while production runs a newer epoch.
6. The attribution insert and the terminal routing-result update must commit in one transaction, rolling both back when the guarded terminal update affects zero rows; a shared `processing_token` predicate alone is not atomic.
